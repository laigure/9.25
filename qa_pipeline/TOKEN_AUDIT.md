# Grounding token 可靠性审计（2026-09-20）

## 当前实际输入是什么

公开 3EED checkpoint 对点云与去空间提示的中性目标描述运行推理。`bdetr.py` 的最后一层 Transformer decoder 输出 `last_query_features`，每个候选框一个 288 维 query。导出脚本用文字与 query 的 64 维对比分支打分，取排名第 1 的 query，再把其 288 维特征输入下游 projector/LLM。模型预测框与该 token 使用同一个 query 索引。GT box 只在导出后做离线核验，不参与 query 排名。

因此层位和维度是对的，但“top1 文字匹配 query 就是被指代物”这一点需要验证。

## 实测结论

全量 Waymo 中性描述 token：train 3,048 个、val 3,082 个；val 单目标 Grounding IoU≥0.25 仅 **47.5%**。扩充后的 v3 验证集中，全部输入目标同时达到 IoU≥0.25 的问答比例为：单目标 **1,505/3,282（45.9%）**，双目标 **155/1,638（9.5%）**，三目标 **0/233**。多目标 QA 不可靠的一个主要来源就是至少一个目标 token 指向了错误框。

在 32 条 train + 32 条 val 的小样本诊断中，val 实际 top1 IoU≥0.25 为 **53.1%**；离线用 GT 在全部 256 个候选里选最佳框的上限为 **96.9%**。说明候选池里通常有合适的框，语言排序经常选错。GT 上限**不能**用作最终模型输入或测试结果。

| 同一批 32 条 val | 至少一个候选 IoU≥0.25 |
|---|---:|
| 文字排名 top1 | 53.1% |
| 文字排名 top5 内取最佳，GT 仅用于离线计算上限 | 81.3% |
| 文字排名 top10 内取最佳，GT 仅用于离线计算上限 | 81.3% |
| 全部 256 个候选的 GT oracle | 96.9% |

把 query 排名的文字 span 从类别名词换成整段中性描述也没有改善：同一批 128 条 val 的 IoU≥0.25 从 **55.5% 降至 51.6%**。不能直接把该选择器作为修复。

## 下游是否使用 token

v2 LoRA 在 355 条固定验证题上，正常/同类别打乱 token 的准确率为 34.08%/33.24%，仅 19 条预测改变，几乎忽视了 token。扩充题型后的 v3 在 373 条题上为 51.47%/47.99%，85 条预测改变，开始利用部分 token，但双目标相对位置测试准确率仅 16.28%。

独立线性探针显示 288 维 token 并非完全无空间信息：v3 的单目标近/远 val 89.4%，自车左/右 val 69.4%。这些是离线诊断头的成绩，不是 LLM QA 成绩。

## 下一步修复方向

1. 保留一目标多个隐式候选：先导出文字排序 top5 的 288 维 query，再训练一个可学习的选择/聚合模块。LLM 仍只接收学习后的隐式向量，不输入 box、中心、距离或显式关系标签。
2. 或仅在 train 序列用 GT object 匹配监督训练 query 重排序器；val/test 时只根据点云、目标描述与候选特征排名，绝不使用 GT 选 token。
3. 先以 Grounding top1/top5 目标定位准确率和同帧多目标“全部选对率”为独立门槛，再训练 QA。报告实际预测 top1 与 top-k 上限，避免把 oracle 上限当最终性能。

上述 top-k/oracle 数据仅为 32+32 pilot，正式架构选择前应在完整 train/val 中复核。
